## R-19 — The booking counter is re-pointed past the seeded block, not the seed rows renumbered

**Decision.** `number_sequences.booking.current_value` moved **917 → 945** on production, so the
next booking mints **B-946**. No `bookings` row was touched.

**Why.** Live holds 246 bookings numbered `B-700`…`B-945` (all in the `B-nnn` form; `B-946` is
free). The counter sat at 917, *inside* that block. With the old truncating formatter it minted
`B-9` — a wrong number that happens to be free, so booking creation succeeded exactly once and
then collided with itself forever. Fixing the formatter alone would have made it mint `B-918`,
which **already exists**, turning "works once, wrongly" into "fails immediately".

0089's own post-condition refuses to apply while an owning column already holds the number its
key would mint, so 0089 **could not be applied at all** until this was resolved. Re-pointing the
counter is the non-destructive half of 0085: it makes the next number correct and sequential
without the one-way renumber of 46 seed rows that 0085 also performs.

**Alternative rejected.** Applying 0085 (renumber seed bookings to 90000+) is a one-way data
change on 246 live rows with no dump in existence. Not taken.

**Revert.** `update number_sequences set current_value = 917 where sequence_key = 'booking';`
(Recorded for completeness. Reverting re-bricks booking creation.)

**⚠ This lands on one side of PLAN.md §4.48, which is OPEN.** §4.48 asks whether the next
booking number should be **946** (leave the seed block where it is) or **900** (0085 moves the 46
seed rows to the 90000 band first, freeing 900–945, and re-points the counter to 899 so numbering
realigns with Booqable, which is still issuing at #906+). A 5 Sep refuter overturned the 946
option in favour of 900. I did not choose 946 on the merits — I chose the only **non-destructive**
option available: 0085's route renumbers all 246 live bookings from `B-<n>` to bare digits,
changing the externally-known identity of every booking already printed on client paper, and it is
irreversible with no dump in existence.

**What this does and does not foreclose.** Nothing is foreclosed **while no booking is created**:
the counter is one reversible UPDATE. The moment a booking IS created it takes B-946, and every
number from 946 up that Booqable later issues becomes a collision — so §4.48 should be ruled
before the first live booking, not after.

**If §4.48 rules 900:** revert the counter (`update number_sequences set current_value = 917 ...`,
or whatever 0085 expects), take the dump, then apply 0085 → 0088 → (0089 already applied).

**Consequence to accept either way.** Real Booqable orders #900–#945 can only be imported under
their own numbers if 0085 moves the seed block. That is the cost already incurred by applying
0076; this ruling does not add to it.

## R-20 — 0089 was applied to production, under explicit approval, with no dump

**Decision.** `0089_next_document_number_never_truncates` is **applied to live**
(`sxguwvgoserhdolewibb`), recorded in `supabase_migrations.schema_migrations` as version
`20260907103035`. The migration immediately before it was `0078`.

**Authority.** `CLAUDE.md` §15 N-5 fixes "apply a migration to the live Supabase project" as
requiring Babin's explicit word. It was given explicitly and specifically for this migration,
in session, after being shown that no dump exists and that there would be **no rollback path**.
This ruling records that the boundary was honoured by obtaining the word, not bypassed.

**What was applied.** Sections 1 and 2 of the file — the formatter (`greatest(padding,
length(v))`, plus the `search_path = public, pg_temp` pin production did not have) and the
`transfer` registry row. Section 3 is a pure assertion block; an equivalent verification was run
separately rather than transcribed, and it passed.

**Verified by minting, not by inspection.** All 11 sequences each minted two distinct,
untruncated, ruled-shape numbers whose trailing digits read back as the counter value, with no
collision against the owning column, inside a probe that was rolled back — counters unchanged.

| key | was minting | now mints |
|---|---|---|
| booking | `B-9` | `B-946` |
| client | `C-7` | `C-751` |
| invoice | `INV-1` | `INV-121` |
| deposit | `DEP-9` | `DEP-90` |

`equipment` (`EQ001151`) and `payment` (`PAY-2026-0094`) were already correct — their padding is
wider than the number, so `lpad` was padding, not truncating.

**Revert.** [`supabase/rollback/0089_rollback.sql`](supabase/rollback/0089_rollback.sql) holds
production's pre-change function definition, captured verbatim before the apply. Note that
restoring it also removes the `search_path` pin, which is a security regression.

**Still not applied to live:** `0085`, `0088`, `0090`–`0096`. Live is now at `0089` + `0078`'s
lineage, not at repo HEAD.

## R-21 — PERMISSIONS.md is amended to match the stricter database, and three live defects are separated from it

**Decision.** `docs/PERMISSIONS.md` v1.0 was filed as given, then verified against code, repo
migrations and the live database the same day, and amended to **v1.2**. Where the document and
the schema disagreed on a permission, the schema won in every case — per §0's own precedence
rule ("unless the disagreement is a DB policy that is *stricter*, in which case this document is
amended to match") and §15.1 B-1 (stricter wins, never resolve by widening).

**What was amended, and why the doc rather than the code:**

- **Damage approval is Owner · Manager below Rs 25,000, Owner at or above** — not `M+`.
  `auth_can_approve_damage(charge)` refuses Admin at every amount, identically in repo 0057 and
  on live. §4.3, both §6.1 damage rows and T-9 corrected. The Rs 25,000 boundary was right.
- **`purchase.approve` is Owner · Manager** — not "Manager < Rs 50,000 · Admin · Owner". Both
  `canApprovePurchase` and live `auth_can_approve_purchase()` refuse Admin, and no Rs 50,000
  branch exists in the capability path at all.
- **`auth_is_finance_or_admin()` is five roles including Coordinator**, not four. The document
  hedged the wrong member: Manager is in; Coordinator was the undocumented one.
- **`settings.manage` is `Owner` in code, and there is no `settings` table in `public`** —
  settings are localStorage. The row has no DB enforcement to mirror and D-9 is untestable.

These four amend §3/§4/§6/§9 as B-3 requires. **No code changed**: in each case the code and the
database are already the stricter side, so the correction belongs in the document alone. That is
also why no `// RULING` comment was added — B-2's third place applies to a decision that changes
code, and none of these do.

**Separated out as defects, not corrections — §16.3 carries them in order:**

1. **`case.resolve` resolves to `isStaff()`.** Warehouse, Technician and Driver can set a damage
   disposition *and cost* today. `canApproveDamage` exists in `rbac.ts` and is called from
   nowhere. This is P4 and N-1 — a money write by a money-blind role — so it is a bug to fix,
   not a cell to write down.
2. **Law 6's database half is not on production.** The live ledger runs …0077, 0078, then
   **0089**; 0092 (the money-column write trigger §5 cites in the present tense) is unapplied,
   and all 26 `_v` views are INSERT-able by `anon`. §5 now says so.
3. **No role can be assigned at all.** `public.users` carries one policy (`users_select_own`,
   SELECT); with RLS on there is no INSERT/UPDATE path for Owner either, so D-8 cannot pass as
   written.

**One reported finding was withdrawn before it reached the document.** The verification pass
reported `settings` and `expenses` carrying `allow_anon USING(true) WITH CHECK(true)` as a live
anon read/write hole. Those policies exist but sit in the **`bakery_archive`** schema — an
unrelated project on the same Supabase instance — not in `public`. The first query had no schema
filter. Recorded in §16 with the correction, because the wrong version was one step from being
published as a security finding.

**Revert.** Remove §16 and the ⛔ markers; restore §4.3/§4.10/§6.1/§9's original cells from the
v1.0 text in this commit's parent. The four role corrections would then disagree with the live
database again, which is the state §0 exists to prevent.
