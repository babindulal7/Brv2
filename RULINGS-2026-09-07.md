## R-19 — The booking counter is re-pointed past the seeded block, not the seed rows renumbered

**Decision.** `number_sequences.booking.current_value` moved **917 → 945** on production, so the
next booking mints **B-946**. No `bookings` row was touched.

**Why.** Live holds 246 bookings numbered `B-700`…`B-945` (all in the `B-nnn` form; `B-946` is
free). The counter sat at 917, *inside* that block. With the old truncating formatter it minted
`B-9` — a wrong number that happens to be free, so booking creation succeeded exactly once and
then collided with itself forever. Fixing the formatter alone would have made it mint `B-918`,
which **already exists**, turning "works once, wrongly" into "fails immediately".

0089's own post-condition refuses to apply while an owning column already holds the number its
key would mint, so 0089 **could not be applied at all** until this was resolved. Re-pointing the
counter is the non-destructive half of 0085: it makes the next number correct and sequential
without the one-way renumber of 46 seed rows that 0085 also performs.

**Alternative rejected.** Applying 0085 (renumber seed bookings to 90000+) is a one-way data
change on 246 live rows with no dump in existence. Not taken.

**Revert.** `update number_sequences set current_value = 917 where sequence_key = 'booking';`
(Recorded for completeness. Reverting re-bricks booking creation.)

**Consequence to accept.** Real Booqable orders #900–#945 can never be imported under their own
numbers — the seed corpus permanently squats them on a UNIQUE column. That is unchanged by this
ruling; it is the cost already incurred by applying 0076.

## R-20 — 0089 was applied to production, under explicit approval, with no dump

**Decision.** `0089_next_document_number_never_truncates` is **applied to live**
(`sxguwvgoserhdolewibb`), recorded in `supabase_migrations.schema_migrations` as version
`20260907103035`. The migration immediately before it was `0078`.

**Authority.** `CLAUDE.md` §15 N-5 fixes "apply a migration to the live Supabase project" as
requiring Babin's explicit word. It was given explicitly and specifically for this migration,
in session, after being shown that no dump exists and that there would be **no rollback path**.
This ruling records that the boundary was honoured by obtaining the word, not bypassed.

**What was applied.** Sections 1 and 2 of the file — the formatter (`greatest(padding,
length(v))`, plus the `search_path = public, pg_temp` pin production did not have) and the
`transfer` registry row. Section 3 is a pure assertion block; an equivalent verification was run
separately rather than transcribed, and it passed.

**Verified by minting, not by inspection.** All 11 sequences each minted two distinct,
untruncated, ruled-shape numbers whose trailing digits read back as the counter value, with no
collision against the owning column, inside a probe that was rolled back — counters unchanged.

| key | was minting | now mints |
|---|---|---|
| booking | `B-9` | `B-946` |
| client | `C-7` | `C-751` |
| invoice | `INV-1` | `INV-121` |
| deposit | `DEP-9` | `DEP-90` |

`equipment` (`EQ001151`) and `payment` (`PAY-2026-0094`) were already correct — their padding is
wider than the number, so `lpad` was padding, not truncating.

**Revert.** [`supabase/rollback/0089_rollback.sql`](supabase/rollback/0089_rollback.sql) holds
production's pre-change function definition, captured verbatim before the apply. Note that
restoring it also removes the `search_path` pin, which is a security regression.

**Still not applied to live:** `0085`, `0088`, `0090`–`0096`. Live is now at `0089` + `0078`'s
lineage, not at repo HEAD.
