## R-37 — Add Bundle answers availability for a window, and the four status pools are gone

**Decision.** PLAN.md **§4.45(a) is closed by option (iii)**, the one it called "a bigger
change". The Add Bundle item picker no longer derives availability from
`product_units.status`. It carries the same operator-picked `?from=`/`?to=` window the Bundles
pane and the bundle detail page carry (§4.44), and asks the same engine
(`queries/productAvailability.readProductAvailability`) that New Rental's equipment picker
already asks. The columns are **Stock · Free · Held**.

**Why not (i) or (ii).** Both collapse ten `product_units.status` members into four pools, and
the premise of both is wrong: `status` is where a unit is *at this instant*, and no arrangement
of a now-count answers "free between two dates". §4.45(a) worried the mapping might mislead an
operator. It already did, and this is the demonstration rather than the worry —

| Screen | Matthews C-Stand 40in, 11–14 Nov 2026 |
|---|---|
| Bundle detail (BND-002), window-aware | **Available 0 of 4**, "On Rent, frees 17 Nov 2026" |
| Add Bundle picker, status-derived | **Stock 4 · Avail 4 · Res 0 · Rent 0** |

One app, one product, one window, two answers — and the wrong one was on the screen where an
operator commits to a kit. The mock's November hold is an `inventory_reservations` row; it
never changed `product_units.status`, so the picker could not see it. That is not a mapping
bug that a better mapping fixes.

Driven after the change, same product: 11–14 Nov reads **Stock 4 · Free 0 · Held 4**, and
20–22 Sep reads **Stock 4 · Free 4 · Held 0**.

**Why the fourth column went.** The engine reports what a booking holds across the window; it
does not split that into on-rent versus reserved, because that distinction is a property of a
booking's stage at an instant, not of a window. A `Rent` column could only be filled by
guessing, so there are three columns and not four. **Held** is `reserved` in the type, renamed
where it is rendered; `onRent` is `0` and `maintenance` is the remainder, which keeps §5.1's
invariant `stock = available + reserved + onRent + maintenance` true by construction rather
than by assertion.

**The quantity half, and why it is the important half.** `productAvailability.ts` answered only
for products with `product_units` rows and reported `unitsOwned: 0` for bulk stock, on the
grounds that "a bulk count is not an availability answer". That was true when it was written
and stopped being true on 7 Sep, when the engine grew `readQuantityHolds` and `capacityFor`.
It is now `productCapacityFor`, and it matters more than the serial half: **live has 204
quantity-tracked products and zero `product_units` rows**, so on production every catalogue row
goes down this path and none goes down the other. A module that answers only for serials
answers for nothing that is actually in the business — and every screen above it was filling
the silence by reporting raw stock as free.

`readProductAvailability` dispatches on `tracking_mode`, going down the unit path for anything
not explicitly `Quantity` or `Consumable` — preserving the safe direction `readProductModes`
already documents, because the unit path can only ever refuse.

**Also corrected, in the same change:** `modules/inventory/EditBundle.tsx` did not compile.
It used `record.isLoading` (the field is `loading`) and passed `title` to `Page`'s Button,
which does not accept it. Both were in commit `98965d0` of 8 Sep, whose message claims
"tsc 0" — that claim was false and is retracted here. The run behind it piped `tsc` into
`head`, so the exit status reported was `head`'s. Gate output is redirected to a file and the
exit code read directly from now on; a pipeline's status is not the compiler's.

**Changed where:** `src/lib/queries/productAvailability.ts` (`mode`, `productCapacityFor`,
dispatch), `src/lib/queries/__tests__/productAvailability.test.ts` (+7),
`src/modules/inventory/AddBundle.tsx` (window, engine read, columns),
`src/modules/rentals/booking/__tests__/itemCatalogue.window.test.ts` (fixture),
`src/modules/inventory/EditBundle.tsx` (the two compile errors), PLAN.md §4.45(a).

**Revert:** restore the `unitsByState` mapping in `AddBundle.tsx` and drop the window control;
delete `productCapacityFor` and its dispatch arm. Both are single, self-contained hunks.
