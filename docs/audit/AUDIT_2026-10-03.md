### 7.1 Method

### 7.2 Result: 3 views leak past RLS
| View | Rows seen by anon | Why |
|---|---|---|
| `audit_logs` (0129) | 2,222 — and **0** from the base table `audit_events` | View runs as owner, so it skips `audit_events_select` (Owner/Admin/Manager only). Carries `old_values`, `new_values`, `diff`, `reason`, `actor_id`. 2,102 rows have values, all matching money/PII key patterns. |
| `staff_directory_v` (0067, 0120) | 5 of 5 | 0120 revokes from `public` and grants to `authenticated`, but anon's default grant is separate and stays. Email/mobile are masked; names, codes, roles, departments, branches are not. |
| `product_units_service_v` (0103) | 220 | `grant select … to authenticated, anon` written explicitly. |

The anon key is public: it is in the client bundle and in three tracked scripts. Anon cannot write to these views (privileges are SELECT/REFERENCES/TRIGGER only; UPDATE returned "permission denied").

**Why it slipped through:** the 20 masking views got row predicates in 0048 and the decision is documented (security_invoker would break the column masks). Views added after 0048 did not inherit that rule, and `check-law6-exposure.mjs` probes money columns by role, not views by anon.

**Fixes (one migration):**
- `alter view audit_logs set (security_invoker = on);` — safe here: it has no masking columns, and the base policy then applies.
- `staff_directory_v`: add `where auth_is_staff()` (the 0048 pattern), or `revoke select … from anon`.
- `product_units_service_v`: `revoke select … from anon` unless a public page needs it.
- Add a gate: for every non-invoker view, assert it has an `auth_*` predicate or is explicitly allow-listed, and probe it as anon with seeded rows.

### 7.3 What I checked and cleared

- 52 files / 69 `SECURITY DEFINER` functions: only `enforce_inventory_reservation_capacity` has no pinned `search_path` in final state (0050 pinned the other two). P2.
- 0 public tables with RLS off. 1 with RLS on and no policy: `staff_auth_pins` — intentional deny-all (PIN access is via RPCs).
- Four non-SELECT policies with `true`: `audit_events_insert` (writes are via trigger and anon insert is revoked in 0091/0093) and three `*_approval_rank` policies (the check clause does the real gate). Not defects.

## 10. Fifth pass: how easy is it to use

### 10.1 Method and honest limit
Static heuristic review of the code: navigation, forms, states, language, keyboard and screen-reader support, and the New Rental flow end to end. **This is not a usability test.** No browser, no real users, no task timing, so I cannot judge visual hierarchy, speed, or whether staff understand the wording. Section 10.5 gives a short test to run.

### 10.2 What makes it easy
- **Blockers are plain and actionable.** New Rental lists every reason Confirm is disabled in a visible card ("No client selected", "Missing client ID or PAN", "Return must be later than pickup"), each with a button that jumps to the fix. The disabled button also carries the same text in `title`, but that is hover-only, so the visible card is what helps on touch.
- **Phone layout is designed, not shrunk.** New Rental has a sticky bottom bar with Save draft and Confirm and a one-line summary (client, item count, total).
- **Modals behave.** Escape closes only the top one, Tab is trapped, focus returns to the opener.
- **Page states exist:** `PageBody` on 40 files, `ErrorBanner` 36, `EmptyState` 27, `RestrictedState` 5, in 152 module files. A skip-to-content link is present, reduced-motion rules exist, and every `outline: none` I checked has a replacement focus ring.
- **Data tables** have a real "Open" button per row, so keyboard users reach rows.

### 10.3 Findings
**U1 (P1). 141 form fields have no accessible name, mostly in the money and incident forms.** 121 `<label>` elements have no `htmlFor` and wrap nothing, so the label is visible but not connected: tapping it does nothing and a screen reader announces an unnamed field. 48 of the 141 fields have only a placeholder, which disappears when typing. Worst: `DeliveryWorkspace` 15, `CouponsManager` 12, `ProductionsList` 11, `LogMaintenanceModal` 10, `LogCaseModal` 8, `CreatePurchaseRequestModal` 7, **`RecordPaymentModal` 5**, plus `RefundPaymentModal` and the `CancelRentalModal` reason box. The shared `Input` already does this correctly (generated id, label, error, helper text); these forms bypass it. Fix: swap to `Input` / `Select` or add `id` + `htmlFor`.

**U2 (P1, blocked on content). The app is English only.** `NE` in `i18n.ts` is an empty catalogue; coverage is 0% and `canEnable()` refuses to switch Nepali on. That is a deliberate, documented decision (PLAN §4.26: wrong Nepali is worse than none), and the machinery is built. If floor staff work more comfortably in Nepali, this is the largest ease-of-use gap, and it needs a Nepali speaker to write the status and action terms first (Pack, Handover, Return, Reset, deposit, damage).

### 10.4 P2
- **U3. Two names for the same thing.** Booking (84 uses in UI copy) and Rental (96): the nav says Rentals, the button says Confirm Booking, the card says Booking Summary. Gear is Equipment 83 · Asset 35 · Item 45 · Product 22 · Unit 33 · Gear 15 · Kit 9. Your UI rules ban only "customer". Add a glossary line to `UI_UX_RULES.md` (one word per concept) and grep to it.
- **U4. Phone keyboards.** 8 phone-like inputs, none with `type="tel"` or `inputMode="tel"`; only 13 of 46 number inputs set `inputMode`. On a phone the wrong keyboard opens for client phone and amounts. Only 7 inputs set `aria-invalid`.
- **U5. 35 of 71 clickable `div`/`span`/`tr`/`li` cannot be reached by keyboard** (no role, `tabIndex` or key handler): `Inventory` 4, `NewRental` 2, `ClientsDirectory` 2, `EvidenceThumbnail` 2, others 1.
- **U6. Two kinds of "discard?" prompt.** `ConfirmDialog` is used in 5 files, but New Rental (2), `RecordWorkspace` and `RecordForm` use the browser's `window.confirm`: different look, different buttons, and a browser can suppress it in an installed or kiosk window.
- **U7. Nav comment is stale.** `nav.ts` says 7 primary + 3 more; the code has 10 primary (Dashboard, Rentals, Operations, Calendar, Inventory, Clients, Crew Assist, Finance, Documents, Analytics) + Tools + Settings. Ten items is a lot for a phone bottom bar; check what `MoreSheet` puts where.

## 11. Sixth pass: design consistency, layout shift, and "finished Return/QC but status does not become Closed"

### 11.1 Method and limits
- **Code trace** of the Return, Reset and Close path, plus a PGlite run on the seeded schema.
- **Headless Chromium** against a production build in mock mode, at 1440, 820 and 390 px. The mock database is **empty**, so I could drive screens and measure layout but **could not run a rental through Return, Reset and Close in the browser**, and I could not reach live Supabase. Everything about the status problem is therefore from code and SQL, not from watching it happen.

### 11.2 Why a finished Return/QC does not become Closed

**What the app does by design.** After Return the booking is `Returned`. Reset (the cleaning and QC job) "changes no stage" (`completeReset.ts`). Close is a separate manual verb: **Close Rental** on Booking Detail, allowed only to Owner, Admin, Manager and Accounts (R-07, R-08). So even a perfect Return plus QC never moves the status by itself. Five things make that feel broken:

**G1 (P0). Most rentals cannot be closed at all, because no screen can return a deposit.**
Close requires `received − refunded − applied = 0` on the deposit. Nothing in the app writes a `Released` or `Applied` deposit movement. `workflow.ts:350` says it outright: "…still held, so the rental cannot close — and no screen records a refund or an application yet". `ReturnSettlementModal`'s confirm button only closes the modal and refetches (`BookingDetail.tsx:3186`); it writes nothing. On the seeded schema `deposit_movements` holds 64 `Received` rows and zero `Released` or `Applied`, and 7 of the 14 `Returned` bookings still hold a deposit. Your own notes put live at 89 deposits across 121 bookings, so a majority of rentals would be refused at Close with "deposit still held". The lifecycle test does not catch it because it closes a booking by direct SQL (L-step "a settled booking closes").
Fix: add a `settleDeposit` action that writes a `Released` or `Applied` movement (with the existing `applied_reason` rule), call it from `ReturnSettlementModal`, and add a lifecycle step Return → Reset → settle deposit → Close through the actions.

**G2 (P1). Staff who cannot close see "Cleaning & Reset" forever.**
At `Returned`, `rentalActions.ts` shows Close Rental to the four closer roles and "Cleaning & Reset" to everyone else. There is no "reset already done" state, so a Warehouse or Technician finishes QC and the same button is still there with the same status. The secondary Reset button on Booking Detail is also drawn only for closers.
Fix: at `Returned` with reset complete show "QC done · awaiting close" for non-closers, and make Reset a one-way job in the UI.

**G3 (P1). Lists do not refresh when a floor job finishes.**
`OperationsShell` emits `RENTAL_RETURNED` and `RENTAL_RESET_COMPLETED`. Only Booking Detail and Today listen. Rentals list, Operations queues, Calendar and Inventory have **0 subscribers**, and they refetch only on a manual Refresh or after a cancel. Finish a Return from a popup opened on the Rentals list and the row keeps its old status until someone reloads. Close has the same gap: `closeRental` emits `RENTAL_CLOSED` and only Today hears it.
Fix: one shared "bookings changed" signal that `useList` for bookings subscribes to, or refetch when the popup closes.

**G4 (P2). The popup claims `Closed` after Reset.** `OperationsShell.tsx` has `STATUS_AFTER.Reset = 'Closed'`, but the database stage stays `Returned`. The popup then closes, so a user rarely sees it, but any code reading `liveStatus` in between gets a false value. Set it to `Returned`.

**Which of these you are hitting depends on the screen and role.** If you were on the Rentals list, it is mostly G3. If you opened Booking Detail as Owner and pressed Close, it is G1. If you were Warehouse or Technician, it is G2.

### 11.3 Design consistency (measured in the browser)

**H1. The page title jumps position between screens.** The title's left edge and top move depending on the page:

| Width | Dashboard | Finance | Rentals, Operations, Inventory, Clients, Documents | Calendar |
|---|---|---|---|---|
| 1440 px, x | 274 | 314 | 326 | 366 |
| 1440 px, y | 111 | 111 | 117 | 117 |
| 390 px, x | 12 | 52 | 64 | 104 |
| 390 px, y | 138 | 142 | 148 | 148 |

So switching tabs moves the heading up to 92 px sideways and 10 px vertically. The cause is the icon tile in front of the title, which is 0, 40, 52 or 92 px wide depending on the page. Fix: one `PageHeader` with one leading-slot width.

**H2. Three "New Rental" buttons on one screen.** Rentals shows a sidebar "+ New", a top-bar split button and a page-header button. Pick one primary.

**H3. The page title appears twice.** The top bar repeats the title that the heading below it already shows (Today / Today, Rentals List / Rentals), and the two sometimes differ (Operations Queues vs Operations; Calendar & Dispatch vs Calendar).

**H4. Developer notes are showing in the UI.** The Rentals footer displays text such as "a return-date range needs a second dateRange the shared filter shape does not carry" and "booking_lines.line_type", with a missing space in "dateRange". The Calendar shows "No holiday calendar is loaded…". Move these to code comments or a help tooltip.

**H5. Small tap targets.** Controls under 40 px: Documents 28, Calendar 36 at desktop and 2 on phone, Rentals 6. This matches E2.

**Layout shift on click: not reproduced.** Layout Shift score was 0 on 7 route loads and 0 on 4 button clicks, and page width did not change. This is weak evidence: the data is empty, so shifts caused by data arriving were not exercised. Static candidates that could shift once data loads: 38 buttons that swap their label while busy ("Closing…") with a fixed width on only 1; 60 places that change font weight on selection (for example the Rentals filter chips 500 to 600); and a body scroll lock that sets `overflow: hidden` without `scrollbar-gutter`, a jump of at most 6 px given the thin scrollbar.

### 11.4 Fix order
1. G1 deposit settlement action plus a lifecycle step through Close. Without it most rentals cannot finish.
2. G3 shared refresh signal. G2 "QC done · awaiting close". G4 one-line fix.
3. H1 single `PageHeader` slot width, then H2 to H4 (copy and duplicates).
4. Run the 5-person test in 10.5, adding "finish a rental and close it" as task 7.
