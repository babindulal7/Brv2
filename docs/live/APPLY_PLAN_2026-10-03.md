## The one-shot seed — `0047` must not be batched

`0047_seed_reference_corpus.sql` is pending, and its own header says:

> Re-applying is NOT a no-op — it is a one-shot seed that FAILS CLOSED … Apply it
> ONCE, into a database that has never held it.

Two things follow. It inserts ~125 rows of reference/demo data into a database that
already holds real rows. And its number `0047` is **already spent on live** by a
different file, `0047_seed_tail_b917_equipment_line` (`20260812155050`) — almost
certainly a split of the same seed, which makes the numeric prefix meaningless as
an identifier for this one file.

The safe failure here is the loud one: the file's internal self-check rolls the
whole transaction back rather than half-applying. The unsafe failure is success.

This needs a decision, not a step. Options, none of them mine to take:

- (a) Live already has the corpus via `0047_seed_tail_b917_equipment_line` — mark
  the local file applied and move on. **Requires confirming the tail file's scope.**
- (b) Live genuinely has no corpus, and demo data is wanted — apply it deliberately,
  alone, in a window where it can be undone.
- (c) Neither — split the file so the shape changes apply and the seed does not.

## What this plan is, precisely

`db:plan` compares names, numeric prefixes, and two structural patterns (a filename
containing `seed`; a numeric prefix already spent on live under a different name).
**It does not read migration bodies for safety**, because whether a file is safe
against a database holding real data depends on what the file does and what is
already there.

Its rename test is a heuristic and has already been wrong once. Ranking candidates
by token overlap produced seven false renames — `booking`, `session`, `inventory`
and `law6` are words every migration here contains — and one of them absorbed
`0047` into the rename bucket, silently deleting the seed hazard above. The test is
now the longest common prefix of *ordered* tokens, which separates the real
`staff_row_for_` rename from `0099 → 0063_create_booking_function`. Those cases are
pinned by `npm run db:plan:selftest`; breaking the rule on purpose makes it fail on
all six plus the missing hazard.

Treat the output as arithmetic. Treat every pending file as unread until it has been
read.
