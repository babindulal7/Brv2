## R-25 — `case.resolve` is a money write, and resolves to Owner · Manager, not every staff role

**Decision.** `checkCapability('case.resolve')` now returns
`rbac.canApproveDamage(ctx.role, 'Manager')` — Owner · Manager. It previously returned
`rbac.canWriteSharedTriage(ctx.role)`, which is `isStaff()`: every staff role, including the three
money-blind ones.

**Why.** `case.resolve` sets a damage **disposition and cost**. A cost is money, so admitting
Warehouse, Technician and Driver breaks **P4** (money-blind is a role property, not a screen
property) and sits against **N-1**. `PERMISSIONS.md` §4.3 as corrected reads *Owner · Manager under
Rs 25,000, Owner at or above*, and `auth_can_approve_damage(charge)` implements exactly that on live
and in 0057 — Admin is refused at every amount (§16 V-3). `canApproveDamage` already encoded the
rule in `rbac.ts` and **was called from nowhere**; this is its first caller.

**Why `'Manager'` is passed as the band.** `checkCapability` receives only the role — the charge is
not in scope. So this gate is the **widest legal set**, and the Rs 25,000 banding stays where the
amount is known: `lib/damage`'s `approverFor(chargePaisa)` on the way in, and
`auth_can_approve_damage(charge)` in the database. **P3 (UI ⊆ DB) holds either way** — this can only
ever be narrower than the policy, never wider.

## R-27 — The Owner, and only the Owner, assigns a staff role; §12.2 D-8's "Admin grants Manager" is refused

**Decision.** `users.primary_role` and `users.is_active` are writable only through
`set_staff_role(uuid, system_role)` and `set_staff_active(uuid, boolean)` —
`0101_staff_roles_are_assignable.sql`, both SECURITY DEFINER, both gated on
`auth_user_role() = 'Owner'`. `public.users` gets **no** write policy, and no INSERT path at all.

**The defect.** `PERMISSIONS.md` §16 V-14: `public.users` carried exactly one policy —
`users_select_own`, SELECT — with RLS on. So **no role could be assigned by anybody, the Owner
included**, and §12.2 D-8 described an outcome the database could not produce. Confirmed by reading
`pg_policy` on the live project, not from a migration file.

It is not a grant problem, which is what makes it easy to misdiagnose:
`has_column_privilege('authenticated','users','primary_role','UPDATE')` is already `true`. RLS
refuses the write by having nothing to say about it — so anything that opens a write here is the
whole gate.

**Why RPCs and not a policy.** Three reasons, increasing in weight: (1) with those grants, an UPDATE
policy makes `email`, `id`, `branch_id`, `client_uuid` and `employee_code` writable by the same
`PATCH` — far wider than the decision; (2) *"at least one active Owner must remain"* is a statement
about the set, and a `with check` sees one row, so the invariant is not expressible in a policy —
and an empty Owner set is unrecoverable precisely because role administration is Owner-only;
(3) the house already answered this on this table — `revoke_staff_pin_for` (0066) and
`record_password_reset_request` (0068) are the same shape, with the same refusal line.

**Who — and the conflict that had to be resolved.** §12.2 D-8 says *"As Admin: … grant Manager →
succeeds"*. **Refused, under §15.1 B-1 (stricter wins).** Four sources say Owner and one says Admin:
`rbac.canManageSettings` is `role === 'Owner'`; `staff_directory_v` (0067) carries
`where auth_user_role() = 'Owner'` inline, so an Admin gets **zero rows** to act on; §11.2 files user
administration under Settings; and §16 V-3/V-4 already caught this same document over-crediting Admin
on the damage and purchase ladders. D-8 was corrected to match the code rather than the code widened
to match D-8.

Three places in the repo said role assignment "needs a ruling" — `UsersRoles.tsx`,
`StaffDirectory.tsx` and `queries/staff.ts`. All three are updated in this change rather than left
to contradict it.

**Deliberately still unbuilt: account CREATION.** Not for want of a ruling. A `users` row without an
`auth.users` identity cannot sign in, and minting the identity needs GoTrue's admin API and therefore
the service key — a complete authorization bypass in a browser. It needs an Edge Function. `0101`
opens no INSERT path, so nothing can half-create a person, and `has_auth_account = false` stays the
alarm it is today rather than becoming the normal case.

## R-30 — The line-ending authority is `.gitattributes`, and the index needs no renormalising

**Conflict.** `STAGE_0.md` S0-2 says to run `git add --renormalize .` and commit the result. Measured
first: the index is **already 100% LF** — 873 entries, zero non-LF, ten binary. Renormalising
therefore changes no blob. Its only effect in this tree would have been to stage the 21 files the
concurrent session had in flight, inside a commit whose stated purpose was line endings.

**Decision.** `.gitattributes` is added and committed alone (`e57d282`); `--renormalize` is not run.
The 186 CRLF files on disk were converted directly, skipping the 9 belonging to the other session's
uncommitted work. `core.autocrlf` is set to `false`, so `eol=lf` in `.gitattributes` is the single
authority in every clone regardless of local config.

**Why.** The churn was never in the index. `core.autocrlf=true` normalised on read, which hid it
rather than preventing it — the ~170-file diff appeared the moment anyone flipped the setting. B-6:
this is the smaller, reversible change, and it does not put another session's work into my commit.

**Two traps worth recording, because both look like data loss and neither is.**

1. After converting line endings, `git status` reported 200 modified while `git diff` reported 23.
   Git takes a size-mismatch shortcut and reports a stat-dirty entry as modified without hashing it;
   `update-index --refresh` will not clear it. Every one of the 176 was verified byte-identical to its
   HEAD blob (`git hash-object` == `git rev-parse HEAD:path`) and then re-added, which rewrites the
   stat cache and stages nothing — `git diff --cached` stayed empty.
2. `git diff --stat` printing only "LF will be replaced by CRLF" warnings and no diff body means the
   diff is **empty**. Four files that looked like uncommitted work in each Claude worktree were CRLF
   phantoms.

**Also under this ruling — the worktree purge (`79f43ac`).** Two dormant `.claude/worktrees/`
checkouts still held the Booqable token in plaintext six days after it was scrubbed from HEAD and all
114 ancestor commits, because **a worktree is a second checkout that does not inherit `.gitignore`**.
Both branches were at `369b373` and fully merged; removed, branches deleted, `.claude/worktrees/`
ignored. The main tree was already clean — zero carriers in `scripts/` and zero in `graft/.cache`.

S0-1's verification grep is **wrong as written**: `[A-Za-z0-9]{10,}` does not match the token, whose
value contains `-` or `_`. Run as specified it prints 0 while the token is still on disk — it would
have certified the purge before it happened. Use `[A-Za-z0-9_-]{10,}`. S0-1's `graft/.cache/`
gitignore entry is redundant; the existing `/graft/` rule already covers it.

**Rotation is still Babin's and has not happened.** The purge makes the value unreachable from this
tree; it does not make it inert.

**Revert.** Delete `.gitattributes` and set `core.autocrlf=true`. The worktrees are not recoverable
and should not be.

## R-31 — A Law 6 write refusal raises 42501, and `0102` guards booking money

**Conflict.** `0092` closed the Law 6 write hole for `products` and `product_units` and raises P0001
(a bare `raise exception`). The same hole was open on `bookings` and `booking_lines`. Two questions:
what error code, and which columns.

**Decision.** `0102_law6_money_blind_cannot_write_booking_money.sql` raises **`42501`**
(insufficient_privilege), which PostgREST renders as HTTP 403 rather than 400, and keeps `0092`'s
message shape so anything asserting on the text `Law 6:` keeps working. **`0092` is not edited** — it
is committed and in the chain, and editing it to chase consistency is worse than the inconsistency.

Columns guarded, read from the schema at the end of the chain rather than remembered:
`bookings.deposit_required`; `booking_lines.rate`, `discount_amount`, `supplier_cost`,
`markup_amount`, `qty`, `days`. Deliberately **not** guarded: `bookings.version` (the optimistic-lock
counter) and `booking_lines.sort_order` (display order).

**Why.** A Law 6 refusal is a permission refusal and should say so on the wire. B-1, stricter wins:
`qty` and `days` are not money columns but they are the two multiplicands of every line total, so
leaving them open leaves the total open (⭐ S0-a; the legitimate partial-pickup case goes through
`booking_line_units`, which this trigger does not touch).

**Verified, PGlite, full chain, before and after.** As a Warehouse seat with the guard absent:
`deposit_required` 5000 → 0 ALLOWED, `rate` 6500 → **1** ALLOWED and it stuck, `qty` → 99 ALLOWED —
while the same seat may not *read* those columns. With `0102`: all four refused, `42501`, message
begins `Law 6:`, rate unchanged at 6500. Both controls hold — a Coordinator still writes the deposit,
and the same Warehouse seat still writes `updated_at`, so floor work is untouched. `check:pglite`
100/100.

**One thing the probe corrected.** `discount_amount → 999999` was already refused before this
trigger — but by a CHECK constraint capping the value, not by Law 6. A smaller discount went straight
through. Coincidental cover is not cover, and a probe that only asks "did it fail?" would have
recorded that column as safe.

**Not closed here:** INSERT. `booking_lines_all` admits a direct Warehouse INSERT carrying any rate.
Stage 1 — it needs a rule about who may add a line at all, which is a permission question, not a
Law 6 one.

**N-5:** not applied to live.
**Revert.** `drop trigger` ×2, `drop function`. One migration.

## R-32 — Completion is counted, and two of S0-8's own measurements were wrong

**Conflict.** `STAGE_0.md` S0-8 specifies the route mapper for the "Real data" dimension as: lazy
imports in `App.tsx`, import tree depth 2, `.from(` / `.rpc(` / `useList` = database,
`src/data/*` = seed. Implemented literally, it does not measure anything.

**Decision.** Two changes, both recorded in `scripts/completion.mjs` at the site:

1. `.from(` also matches **`Array.from(`**, which appears 89 times in `src/`. The first run reported

**Two deviations from the letter of S0-8, both deliberate.** The suite (~18 min) and `check:pglite`

## R-33 — `client_uuid` is an idempotency key, not a tenant id (recorded, not decided)

Not a ruling so much as a correction to a reading that cost time and would cost more. `unique
(client_uuid)` sits on **114 tables** on that column alone, which reads like a schema disaster — one
row per tenant, forever.

It is not. Law 8 — "every write carries a `client_uuid`; duplicates rejected" — is an **idempotency**
rule: the writer generates a fresh UUID per write and a replay is refused. The chain's own seed
proves it, with 6 `inventory_categories` rows across 6 distinct values. Any harness or fixture that
reuses one value across two rows of a table will be refused, and that refusal is correct.

Recorded here because the wrong reading produces a false P0, and because the right one is a hard
constraint on every test harness that seeds rows directly.

## R-34 — A bundle is editable; a saved component is not removable, and no control pretends otherwise

**Decision.** `/inventory/bundles/:bundleRef/edit` and `actions/inventory/updateBundle.ts` ship
with everything the grants permit — name, description, category, both rates, active/archived, and
each component's quantity, days and mandatory flag, plus adding new components — and **no removal
control at all**. The gap is stated on the screen in plain words and filed as **PLAN.md §4.52**.

**Why.** `authenticated` holds SELECT, INSERT and UPDATE on `bundles` and `bundle_items` and **no
DELETE** on either (`information_schema.role_table_grants`, read 8 Sep and re-read after `0079`-`0103`
landed on production the same day — the post-wave state, not a snapshot they have since moved;
`anon` lost INSERT and UPDATE on both in that wave). `bundle_items` has no archive
column, and `bundle_items_qty_positive` refuses `quantity = 0`. So the three ways a component
could be retired are each closed by a different rule, and closing any of them is Babin's:
granting DELETE is **§15.2 N-4**, adding the column is a migration under **N-5**.

The alternative — ship the button and let it fail — is worse than it sounds. A `.delete()` the
role has no grant for is refused by Postgres, but a delete matching zero rows returns **no error**:
the screen would report the component removed and the next load would show it still there. B-1
(stricter wins) and the UI ⊆ DB rule both land on absent.

**Two smaller decisions inside the same build, recorded so they are not re-litigated:**

1. **`inventory.update` is a new capability string**, mirroring `bundles_manage` ∩
   `bundle_items_all` = Owner · Admin · Manager — the §4.20 method, re-read from live rather than
   copied from `inventory.create`. It lands on the same three roles; it is named separately
   because it is a different act, and if edit is ever narrowed without create being narrowed,
   `rbac.canUpdateBundle` is the one line that changes. N-3 holds: it is not wider than RLS.
2. **The edit screen's component picker draws no availability**, which is what keeps it clear of
   the still-open §4.45(a). That ruling is about the four count columns an item picker renders and
   how ten `product_units.status` members collapse into them. This picker renders none of them —
   name, asset code, category, and rate for a money-visible session. It cannot tell an operator
   gear is free, so it cannot tell them wrong. Availability stays where §4.44 put it: against a
   window, on the bundle's own page.

**Changed where:** `src/actions/inventory/updateBundle.ts` (new), `src/modules/inventory/EditBundle.tsx`
(new), `src/lib/rbac.ts` (`canUpdateBundle`), `src/actions/core.ts` (`case 'inventory.update'`),
`src/events/eventBus.ts` (`BUNDLE_UPDATED`), `src/lib/queries/bundles.ts` (`categoryId`),

## R-26 — Reservations are written by the database, not the app

**Source:** Babin's 8 Sep addendum, filed here on the day. **Status:** BUILT — `0099`, `0100`,
`confirmRental.ts`, `lib/queries/availability.ts`. Not applied (N-5).

**Ruling.** A booking holds inventory from the moment it becomes **Booked**, and Postgres writes
that hold. `inventory_reservations` gains a trigger writer; the app stops inserting reservations
and keeps only a pre-check that produces a friendly message before the transition is attempted.
Quotes hold nothing — a Quote may overlap another Quote.

**Why, reproduced before it was fixed.** PGlite, full chain, 8 Sep: two bookings for the same
unit over overlapping dates (10–12 Sep and 11–13 Sep) both reached Booked and
`inventory_reservations` stayed at **0 rows**. The GiST constraint
`inventory_reservations_no_double_booking` (0003) and the capacity trigger (0045) guard a table
only `confirmRental.ts → reserveAssignedUnits` ever filled, and any of the five roles admitted by
`booking_stage_transitions_insert` bypasses it with one PostgREST call. P0.

**Landed**

## R-28 — Preventive maintenance: due by time or usage, warn only, interval per product model

**Source:** Babin, 8 Sep, three tappable questions. **Status:** database half BUILT (`0103`);
UI half partly built, see below. Not applied (N-5).

**Ruling.**
1. A unit is **due for service** when **either** its elapsed-time interval **or** its usage
   interval since the last completed preventive job is reached — whichever comes first.
2. Being due **warns only**: a `Service due` badge, `Overdue by N days` past a grace window, and
   the unit **stays bookable**. Nothing moves it to Maintenance; no work order is created.
3. The interval lives on the **product model**, not the category and not the unit.

Derived, never stored: no `is_due` column anywhere.

**Landed**

| Layer | What |
|---|---|
| `0103_preventive_maintenance.sql` | `products` gains `service_interval_days`, `service_interval_rental_days`, `service_interval_meter_hours` (all nullable — null means that trigger is off) and `service_grace_days` (default 7 ⭐). `product_units` gains `meter_hours_recorded_at` and `service_meter_baseline`. A trigger re-bases the meter when a `Preventive Service` job completes — and only then. View `product_units_service_v`, money-free by construction and revoked for DML per 0095. |
| `src/lib/serviceDue.ts` | The reading rule: which token, which words, which counters. Decides nothing about whether a unit is due — the view owns that arithmetic and there is exactly one copy of it. |
| `src/lib/queries/serviceDue.ts` | `readServiceDue(unitIds)` (never throws — a warning must not take a screen down) and `readUnitsDueForService()` (does throw — it IS the screen). |
| `src/components/ui/ServiceDueBadge.tsx` | Wrench icon + words + tone, in that order of reliability. Renders **nothing** when nothing is due. |
| Asset Detail · Packing Queue · Inventory ▸ Maintenance | The badge beside each unit; the amber `Service due — still OK to send` line under a packing row; a live `Due for service` card. |
| `docs/PERMISSIONS.md` §4.3 | `inventory.edit_service_plan` (Owner · Admin · Manager), `inventory.record_meter` (M+ · Warehouse · Technician), and the view readable by all staff. |

**Three deviations from the ruling's schema table, each stated in `0103`'s header.**
(a) The meter already exists as `product_units.running_hours numeric(10,2) NOT NULL`; a second
hours column would give one unit two meters that could disagree. (b) A delta needs a baseline, and
the ruling names no place for the reading at service time — `service_meter_baseline` is that
place, and its reset trigger is the ruling's "a completed Preventive row IS the reset" made
executable. (c) The enum member is spelled `Preventive Service`, one of the eight locked types;
nothing was added to the enum.

**`due_at` carries the time due date only.** The instant usage crossed its threshold is not
recoverable without replaying every booking's transitions per unit on every list read. The usage
case is served by the counters instead, which is what the ruling's own tooltip shows —
`— usage (42 of 40 rental days)` names no date. `overdue_days` is null for a usage-only reason
for the same reason. When both thresholds are crossed, `due_reason` reports `'time'`: it is the
one that carries a date an operator can act on.

**Verified.** `0103`'s post-conditions execute the ruling's own scenario against a real Postgres
and roll it back: a model on 90 days / 40 rental days, a unit serviced today, five bookings of ten
rental days each → `due_reason = 'usage'` at 50 rental days although the calendar has 40 days to
run; a completed `Repair` does **not** reset the clock; a completed `Preventive Service` does, and
the counter returns to 0. Also asserted: the view is money-free, is not writable by
`authenticated`, and returns a null `due_reason` for every model with no plan. 15 vitest cases on
the reading rule.

**Not built, and why.** The `Create job` row action renders through `Unavailable` with its reason
— `createMaintenanceJob` is `implemented: false`, and this repo's rule is that unbuilt renders as
Unavailable, never as a fake success. The model page's `Service plan` card, the two Reports rows
and the Tier-1 Technician notification are not built; they are in this session's Remaining list.

**Revert.** Drop the four `products` columns, the two `product_units` columns, the view and the
trigger; delete `serviceDue.ts` ×2 and `ServiceDueBadge.tsx`; remove three call sites. Data in
`maintenance_records` is untouched throughout.

## R-35 — The lifecycle runs in CI against a real Postgres

**⚠ Issued by Babin as “R-27” in the 8 Sep addendum.** `R-27` in this file was already taken, the
same day, by a concurrent session's staff-role ruling. Numbers are not reused (the same rule that
governs migration numbers), so the lifecycle ruling is filed here as **R-35**. Both R-27s are
real; neither supersedes the other; this note is the cross-reference in both directions.

**Status:** BUILT — `scripts/e2e-lifecycle.mjs`, `npm run check:lifecycle`, wired into
`.github/workflows/ci.yml` beside `check:pglite`.

**Ruling.** The audit's PGlite probe becomes `scripts/e2e-lifecycle.mjs` and runs in CI. A red
lifecycle blocks merge. It is the first thing run after any migration is added.

**Why.** 2,834 unit tests were green while the database accepted a double booking, refused **every
discounted booking**, allowed a stage walk with no floor rows, and allowed a close with no invoice.
Unit tests mock `lib/supabase` or drive `lib/mock/client.ts`; every one of those four failures
lives on the far side of that seam — in an enum cast, a trigger, a policy, a constraint.

**The thirteen steps.** L1 create with a 10% discount · L2 Booked writes one reservation ·
L3 an overlapping second booking is refused · L4 same-day turnaround accepted · L5 quantity beyond
stock refused · L6 the floor walk · L7 a partial return · L8 the invoice arithmetic, recomputed in
the script and never read back · L9 four payments that must be refused · L10 two payments settle ·
L11 Closed needs a settled invoice · L12 the money-blind sweep · L13 audit and payments immutable.

**Known-red is a first-class outcome, not a skip.** A step marked `expect: 'red'` that fails is
reported and does not fail the run; a red step that **passes** fails the run loudly, because the
behaviour was built and the marker has become a lie. R-27's own words — "records the current
behaviour as a known-red row rather than skipping it".

**First run, and what it found.** 9/13 green, 4 known-red, 0 failed. It found two defects that no
reading had:

- **`create_booking` refused every discounted booking for a second, independent reason.** With the
  `audit_event_class` enum fixed, the call still failed for Coordinator and Warehouse and not for
  Owner: `INSERT … RETURNING` applies the table's SELECT policy to the row it returns, and
  `audit_events_select` admits Owner · Admin · Manager only. Fixed in `0099` by minting the key
  instead of reading it back — not by widening the policy (B-1).
- **L9: two of four payments the database must refuse, it accepts** — an amount larger than the
  outstanding balance, and a payment naming another client's booking.

**Limits, stated in the file's header.** PGlite is not Supabase: no JWT, no PostgREST, no
`auth.uid()`, no production column grants. RLS *is* exercised (`set role authenticated` +
`app.current_user_id`, the same shape `0094`'s post-conditions use), but every green here is a
necessary condition and never a sufficient one.

**Revert.** Remove the workflow step. The script stays.

## R-36 — Booqable is out. This is a standalone system, and no table has a second owner

**Decision.** Babin, 9 September 2026: *"now dont sync with booquable make it complete app in its
own."* The Booqable integration is removed entirely — code, edge functions, import scripts and the
data-ownership switch. Babin Rentals OS masters all of its own data.

**What was actually there.** The bridge was 8,949 lines across twelve files in `src/lib/booqable/`
with **zero importers anywhere in `src/`** — it had never been switched on. But it was not
harmless, because `lib/dataAccess.ts` carried a live **source switch** that classified eight tables
as Booqable-owned:

* read-only to the OS — `products`, `bundles`, `bundle_items`, `product_units`, `external_invoices`
* writable only through six push functions — `clients`, `bookings`, `booking_lines`

`insertViaSourceSwitch` / `updateViaSourceSwitch` **threw** for all eight, naming a bridge function
to call instead — functions that, after the deletion, would not have existed. That switch is the
thing that made the app not standalone, and it is gone. **Every table is now `os-native`**;
`idempotentInsert` and `safeUpdate` are the write path for all of them, unchanged.

**Removed:** `src/lib/booqable/` (12 files), `supabase/functions/booqable-proxy` and
`booqable-webhook`, seven import/sync scripts including the quarantined `full_sync.sql`, and the
switch itself — 20 files, ~11,000 lines.

**Kept, deliberately.** `external_refs` (171 rows) and `external_invoices` keep every row: Law 3
does not delete history, and `external_refs` is the only record of which Booqable order each of the
200 imported bookings came from. Nothing writes either table now, and `check-db.mjs` says so rather
than naming a module that no longer exists.

**This closes PLAN §4.48(a),** which asked *"May the OS mint booking numbers 900-945 while Booqable
is still issuing?"* — option (1), the spec literal. Booqable is not issuing anything, so there is
no band to reserve and no back-fill to collide with. That is already the state on production:
`0085` is applied, the counter is 899, and the next booking is **900**. §4.48's warning that the
question had to be ruled *before the first live booking* is honoured — no booking has been created
since, so nothing is foreclosed.

**Not done here, and it needs Babin.** The `booqable-proxy` edge function is **still ACTIVE on the
live project** and holds the API token as a secret. Deleting a deployed function is not something
this session can do; it is one action in the Supabase dashboard, and doing it also retires the
token that the 5 Sep audit found in the working tree — better than rotating a credential for an
integration that no longer exists.

**Verified.** `tsc --noEmit` 0 · `eslint --max-warnings 0` 0 · the full suite green ·
`check:pglite` and `check:lifecycle` unchanged (no migration was touched).

**Revert.** `git revert` this commit. The bridge comes back whole, and `dataAccess.ts`'s switch
with it; the eight tables are Booqable-owned again and the two wrapper functions throw again.
