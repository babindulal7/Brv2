## R-39 — Ease of use is the #1 product priority, and it is measured in taps

**Babin, 19 Sep 2026, verbatim:** *"max prority to the app is user should use this in few
clicks and ease of use make every thing easy in tje app"*.

**Decision.** Fewest clicks wins. When two designs both satisfy the laws and the specs, the
one that costs the operator fewer taps ships. A flow that costs more taps than it must is a
**defect**, filed like one — ranked above visual polish, ranked below the seventeen laws.

**What this never touches.** B-1 stands: stricter wins. A permission gate, an approval, a
named-action confirm on an irreversible step (Cancel · Void · Reverse) or a legal gate is not
"friction" and cannot be removed under R-39. R-39 removes *avoidable* steps only — redundant
confirms, re-typing what the system already knows, navigations that could be a modal, fields
that could have been defaulted.

**Defaults are doctrine.** Every form opens with the most probable answer already in it and
every screen answers "what would 90% of operators do here?" A field that could be defaulted
but is not is a defect under this ruling. Examples already in force: payment amounts prefill
from outstanding, dates default to today, scan loops accept without per-item confirms.

**Tap budgets — ⭐ defaults under B-5, flippable by reply.** A tap = one pointer action or
scan event. Typed characters are not counted; the number of *typed fields* is reported
separately. The count runs from the screen where the operator forms the intent to the
committed success state, including the tap that opened the flow:

| # | Flow | Budget |
|---|---|---|
| 1 | Mark one item on the floor (Pack · Handover · Return · Reset) by scan | **1 act** — the scan itself commits the mark; no per-item confirm |
| 2 | One floor stage committed for a booking, from its Today row | **≤ 3 taps** beyond item scans (open workspace → review → confirm) |
| 3 | Record a payment from any booking surface | **≤ 4 taps**, amount and method defaulted |
| 4 | New client created inline inside New Rental | modal, **≤ 3 required fields** at open |
| 5 | New Rental happy path, Dashboard → Booked (existing client, one item, default dates) | **⭐ ≤ 12 taps** — provisional, set before measurement; the audit in PROGRESS 2026-09-19 (c) either confirms or re-budgets it |

**Dirty-state guards are excluded from budgets by design.** The `beforeunload` / unsaved-changes
prompts added 18 Sep cost a tap only when they save work; that tap is a feature.

**Why now.** The build was already moving this way without the mandate on paper: the 17 Sep
nav cut (11 → 7 primary items), the Operations popup (floor verbs without full-page
navigation), the header `Create ▾`. R-39 makes the direction the stated top priority so every
session converges instead of drifting.

**Enforcement.** From this session: (a) new screens and flows land with their tap count
stated in the session's PROGRESS entry; (b) any existing flow measured over budget is filed
as a defect with a named fix; (c) the measured baseline for the flows above lives in
PROGRESS.md under 2026-09-19 (d), made the same day so the budgets are anchored to the real
app, not to memory.

**Changed where:** PLAN.md §4.57; CLAUDE.md (top-priority note). No code site — policy ruling.

## R-40 — An undefined `var(--token)` reference is a rendering bug, and the soft-callout pairs are named

**Context.** UI Consistency Phase 2 (Rentals migration) ran a scan of every `var(--x)`
reference in the in-scope files against the definitions in `src/styles/`. Six references
pointed at tokens that do not exist; two more were defined-by-alias to a *solid* status
colour where the call site expected a soft wash. An undefined custom property does not
error — the declaration computes to `unset` and the element silently inherits — so every
one was a live defect that compiled clean (theme.css's "alias registry, 22 Aug audit"
records the same class of bug being fixed once already, and it re-entered since).

**Decision.**

1. **A `var(--token)` whose token is undefined is a bug at the reference, not a style
   choice.** Fix = point the reference at the canonical token. Never "fix" it by defining
   a new module-scoped token; new tokens are added only in `styles/theme.css`, with both
   themes, in the same commit as their first call site.
2. **The soft-callout pairs are named, so no screen invents another:**
   - caution/warning → `--chip-amber-bg` + `--chip-amber-fg` (border via
     `color-mix(in srgb, var(--chip-amber-fg) 35–40%, transparent)`);
   - danger wash (row needs attention, field in error) → `--danger-soft` +
     `--danger-text`, border `color-mix(in srgb, var(--danger) 35%, transparent)`;
   - selected row/chip → `--nav-active-bg` (+ `--nav-active-accent` text) only;
   - muted/recessed → `--card2`;
   - inline error banners use the SOLID pair (`--st-danger-bg` + `--st-danger-fg`),
     the `ErrorBanner`/RecordPaymentModal shape — never `color: var(--danger)` on
     `--st-danger-bg`, which is red-on-red.
3. **`--amber-text`, `--danger-border`, `--surface-muted`, `--surface-active`,
   `--chip-neutral-bg`, `--st-warning-*`, `--focus` are not tokens** and stay
   un-invented; their call sites were repointed in the same pass.

**Changed where:** `rental-timeline.css:11` (`--input-focus`), `rentals.css:74`,
`FastReturnModal.tsx` (×4), `BarcodeLookupModal.tsx`, `CancelRentalModal.tsx`,
`RentalsList.tsx:2258-2267`, `BooqableRentalFilterDrawer.tsx:151`. `// RULING`-style
comments sit at each site. Logged in PROGRESS 2026-09-19 (c).
