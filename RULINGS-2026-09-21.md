## R-40 — Stage transitions are fail-closed; a floor verb seals only what the database confirms

**Decision.** `booking_stage_transitions` inserts are written with `queueOnFailure: false`
(new option in `dataAccess.ts`): **never queued offline, never optimistically accepted on a
`Failed to fetch` / 408.** A stage transition commits or throws — there is no third outcome.

Pack / Handover / Return then **read `bookings.stage` back** inside `floorVerb.advanceStage`
before anything seals — the same guard `confirmRental` (`readStage`) and `closeRental` already
carried (RL-08, now closed). A stage the database cannot be seen to have reached is reported
exactly like a refused one: the session stays `In Progress`, the error names it, the next
press resumes.

**Why.** Audit-01 P0-01: offline or a dropped response made `idempotentInsert` queue the
transition and return optimistic success; `floorVerb` believed it, sealed the session
`Completed`, and told the operator the handover/return happened. The booking had not moved.
Custody actions must not ride a best-effort queue.

**What did not change.** Ordinary operational rows (session lines, movements, notes) may
still queue and drain — nothing downstream of them claims a stage moved. Retry safety is
unchanged: the caller's Law 8 key makes a retried press hit the 23505 duplicate branch and
resolve to the row that landed, never a second transition.

**Changed where:** `src/lib/dataAccess.ts` (`InsertOptions.queueOnFailure`, two guarded
branches), `src/lib/bookingTransition.ts` (passes `queueOnFailure: false`),
`src/actions/rentals/floorVerb.ts` (`advanceStage` read-back + step-7 comment); positive
control test in `__tests__/floorVerbs.test.ts` ("does not seal when the stage cannot be read
back at the new value").

**Revert.** Remove the options argument and the read-back block. Do not do this silently —
that revert re-opens P0-01.

## R-41 — The close gate counts pending damage at the database (not just the app)

**Decision.** `apply_booking_stage_transition()` refuses `Returned → Closed` when any
non-voided `damage_findings` row stands at `'Pending Approval'`, through either parent
(`return_lines → booking_lines → booking`, or `cleaning_queue_entries.booking_id`) —
`GATE:gate.close.damage_pending`. This mirrors the app-side RL-06 gate
(`workflow.ts closeGates.damageChargesPendingApproval`) one level down, where no API path,
RPC, or hand-run SQL can walk past it. A return-inspection finding raises no case
(0003:484), so the existing "no open cases" gate structurally cannot see it.

**Why.** Audit-01 P0-02. `0003:399` always intended unsettled damage to block Close; 0116
implemented five of the six checks.

**Consequence, stated.** A booking that has a pending finding cannot close until the finding
is approved or dispositioned — and the approval surface that writes
`damage_findings.approval_state` is **still not built** (TODO(FORMS-05), noted in
`workflow.ts`). Approving findings is the next required build, or those bookings are stuck
by design.

**Changed where:** `supabase/migrations/0131_close_gate_pending_damage.sql` (full-body
replace of `apply_booking_stage_transition`; the rest of the body is 0116 verbatim).

**Revert.** Re-apply 0116's function body.

## R-42 — `completePickup` is retired (`implemented: false`)

**Decision.** The alternate one-tap checkout is off. It auto-packed and auto-handed-over
every line AND passed `governmentIdVerified: true` / `bookingAuthorizationVerified: true`
that nobody verified — fabricated compliance facts inside an append-only operational record.
There is exactly one checkout path: the Handover Workspace → `runFloorVerb('Handover', …)`,
where ID checks, signatures and the R-06 money override are operator-supplied inputs.

**Why.** Audit-01 P1-03. The action had no UI caller, and `MovementList.tsx` already
described it as the disabled stub it was supposed to be; the flag now matches the prose.

**Changed where:** `src/actions/rentals/completePickup.ts` (`implemented: false` + header);
pin test added (`__tests__/completePickup.test.ts` asserts the dispatcher-facing flag).
Export retained because `actions/rentals/index.ts` re-exports it; delete the file outright
when its legacy test file is retired.

**Revert.** Flip `implemented` back to `true` — and in the same ruling explain where
`governmentIdVerified: true` legitimately came from.

## R-43 — Booking creation is ONE transaction, crew and transport included

**Decision.** `create_booking(jsonb)` now also writes `booking_crew_lines` and
`booking_transport` inside its transaction (migration `0132`, rebased on 0119 verbatim).
The client-side post-RPC tail is deleted; `CreateRentalPartialError` no longer exists,
because the state it named — a Quote without its crew or its delivery — can no longer
exist. Either everything lands or nothing does. RLS is unchanged (SECURITY INVOKER; the
caller faces the same policies as the old PostgREST path — refusals now roll back whole).

**Why.** Audit-01 P1-02: `NewRental`'s recovery for a partial create was "press Confirm
again", which confirmed the incomplete Quote rather than completing it — and BookingDetail
has no edit path for either table to repair one afterwards.

**Changed where:** `supabase/migrations/0132_create_booking_crew_transport.sql`;
`src/actions/rentals/createRental.ts` (payload carries `crew`/`transport`; result reads
`crew_lines` / `transport_written` from the transaction; the partial-error class removed);
`src/lib/mock/client.ts` (`create_booking` local mirror amended — the seam rule);
`NewRental.tsx` (partial-error branch removed); `createRentalCrewTransport.test.ts`
rewritten for the new contract.

**Known pre-existing seam drift (not introduced here, not fixed here — needs a ruling):**
`createRental` sends `booking_no` when confirming a draft; the mock honours it, but the SQL
function has minted `next_document_number('booking')` unconditionally since 0063. The two
halves disagree about draft-number reuse.

**Revert.** Re-apply 0119's function body and restore the client-side post-RPC writes.
